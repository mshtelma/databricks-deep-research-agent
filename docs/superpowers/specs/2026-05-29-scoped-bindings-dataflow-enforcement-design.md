# Spec: Scoped Bindings & Dataflow Enforcement for Generated Workflows

**Status:** Design approved 2026-05-29 — pending user spec review.
**Author:** Michael Shtelma + Claude (Opus 4.8).
**Scope:** Make the workflow framework *less permissive* about dataflow by introducing lexically-scoped bindings over the composition tree, a build-time checker that enforces "nothing read from nowhere, nothing wasted" across all three dataflow channels, a single dataflow IR rendered for both humans and a repair LLM, and — gated by a measured-complete checker — free-form topology synthesis by a frontier model instead of catalog selection.

---

## 1. Context & motivation

### 1.1 The triggering defect

Deployed custom agent `87457a7f-6c9c-4d62-8fa8-92024482ab91` (AIS production) is a
plan-and-execute workflow. Inspection of its `definition` AST showed:

- Its research body is a **sequence** of `researcher → reflector`.
- The body `reflector` (labelled "Critic") writes `output_key="reflection"`.
- The loop is **not** driven by that reflection. The plan-and-execute runtime
  drives continue/replan/complete off a *separate* `evaluator` agent whose
  return value is parsed directly
  (`plan_execute_runner.py:475` — `normalize_evaluation_decision(extract_decision(evaluator_output.content))`).
- The body reflector's `reflection` text *is* read — but only by the
  synthesizer (`workflow_builder.py:2012`, `input_keys=[..., "reflection"]`).

So the body reflector is **half-dead**: its control decision is discarded
(the runtime never reads it — the body is executed for side-effects only,
`plan_execute_runner.py:397-402`), and its textual output duplicates work the
evaluator already does. It costs one analytical-tier LLM call per research step
and contradicts the builder's own docstring, which describes the intended shape
as "planner/direct-researcher/evaluator" with no body reflector
(`workflow_builder.py:1809`).

This is not a one-off bug. It is a symptom: **nothing in the framework checks
that produced values are consumed, or that consumed values are produced.** The
builder can emit a node whose output goes nowhere, and nothing complains.

### 1.2 The general problem

The framework composes workflows as a **tree** of nodes — composites
(`sequence`, `parallel`, `loop`, `conditional`, `plan_and_execute`,
`subworkflow`) and leaves (`agent`, `tool`). Data moves between nodes through
**three distinct channels**, and only a fraction of one channel is checked
today:

| # | Channel | Producer | Consumer | Checked today? |
|---|---------|----------|----------|----------------|
| 1 | **STATE** | a node's `output_key` | another node's `input_keys`, or a condition key | Conditions: partially (`condition_contracts.py`). `input_keys`: **no**. |
| 2 | **POOL** | `pool_writes` | `pool_inject` | **No** |
| 3 | **RUNTIME-RETURN** | a child node's return value | a container reads it directly in Python | **No** (invisible to any static check) |

Channel 3 is the subtle one. A container like `plan_and_execute` does not read
its evaluator's decision from STATE — it calls the evaluator and inspects the
returned object in runner code
(`plan_execute_runner.py:463-477`). This edge exists only in the runtime; no
AST field represents it. Any checker that models only STATE will be **blind**
to it, and will mislabel a control output as "dead" when it is in fact the most
important edge in the loop.

### 1.3 Two kinds of output

The dead-store analysis must distinguish:

- **Data outputs** — consumed by being *read* (via `input_keys`, `pool_inject`,
  or a container reading a return value). A data output that nobody reads is
  genuinely wasted.
- **Control outputs** — a value whose only purpose is to make a *container*
  branch (loop continue/break, conditional route). A control output is
  "consumed" iff some enclosing container actually branches on it. The body
  reflector's `reflection` *looks* like a control output (it's a reflector's
  decision) but no container branches on it — that's what makes it dead.

The framework currently cannot tell these apart, so it cannot tell a
legitimately-terminal output (e.g. the top-level synthesizer's `report`, which
is the workflow result and is *supposed* to have no in-graph consumer) from a
genuinely-wasted one.

### 1.4 Why now / why this shape

Two facts make an aggressive fix safe and worthwhile:

1. **No install base.** These workflows are generated by *our* builder and
   stored in *our* database. There is no third-party consumer of the AST whose
   workflows we'd break. We can tighten the framework's resolution rules
   directly rather than layering a validator-fiction on top of permissive
   runtime semantics.
2. **State is immutable to consumers.** When an agent reads a state key it
   receives a **serialized copy** (`harness.py` `_build_input` serializes at
   read; `StateEntry` is `@dataclass(frozen=True)`, `state.py:45`). The log is
   append-only with last-writer-wins per key (`_latest_index`,
   `state.py:131-133`). So the dataflow is effectively **SSA-like**: every
   write is a fresh binding; nobody mutates a shared cell. This means scoping
   is a change to **name resolution only** — not to storage, not to mutability.
   It cannot introduce data races or aliasing bugs because there is no aliasing
   to begin with.

### 1.5 The thesis

Today the builder picks from a small catalog of hand-written topologies
(`single_agent`, `parallel_lanes`, `plan_and_execute`). That is a drawback: a
frontier model is capable of synthesizing a *correct* topology for a query, but
we constrain it to ~3 shapes because we have no way to *check* an arbitrary
shape. The catalog is a workaround for a missing verifier.

The plan, in one sentence: **build a dataflow checker complete enough that we
can trust a frontier model to synthesize arbitrary topologies, gated by the
checker** — the compiler/type-system pattern (the model writes typed-node ASTs;
the checker enforces them; bad programs don't compile).

Lexically-scoped bindings are the enabling substructure: they shrink the
namespace each node sees to its own block (plus explicit imports), which (a)
makes "read from nowhere" a local, decidable question and (b) makes large
nested workflows comprehensible the way block scope makes large programs
comprehensible.

### 1.6 Goals

1. **Enforce dataflow correctness at build time** across all three channels:
   no dangling reads ("read from nowhere"), no dead stores ("nothing wasted"),
   with control-vs-data severity tiers.
2. **Lexically scope the namespace** to the current block; outer-block bindings
   are hidden unless explicitly exported. Imports/exports are *auto-derived*
   from existing `input_keys`/`output_key` declarations (no new authoring
   burden, no breakage of current generated workflows).
3. **Visualize the dataflow** — one IR, rendered as a DAG for humans and as
   text for a repair LLM.
4. **Unlock structured freedom** — once the checker measures zero false
   negatives across the topology×domain matrix, let the frontier model
   synthesize free-form topologies, gated by the checker.

### 1.7 Non-goals

- Changing state **storage**, mutability, or the append-only log. Resolution
  only.
- A general dataflow language or user-authored import/export syntax. Imports
  and exports are derived, not written.
- Replacing `condition_contracts.py`'s availability lattice — we **extend** it.
- Runtime enforcement. All checks are build-time; the runtime is unchanged
  except for Phase 0's node removal.
- Hardcoding any domain or topology (per project constitution: structural
  contracts only, never worked examples or category lookups).

## 2. Core model — the Scope Tree IR

The checker operates on one intermediate representation derived from the
workflow AST: the **Scope Tree**. It mirrors the composition tree (every
composite node opens a scope; leaves bind/read within their enclosing scope)
and carries, at every node, the three channels and an availability lattice.

### 2.1 Bindings, reads, and the three channels

A **binding** is a (key, schema, producer-node-id, availability, origin) tuple
created when a node declares an `output_key` (STATE), a `pool_writes` entry
(POOL), or is a container child whose return value a container consumes
(CONTROL). This reuses the `Binding`/`ValidationScope` vocabulary already
present in `condition_contracts.py:299-354`.

A **consumption edge** connects a binding to a node that reads it, and carries a
**kind ∈ {data, control}**:

- A **control** edge exists iff an enclosing container *branches* on the value
  (loop `until`/`min_iterations`, conditional route, or plan_and_execute
  evaluator return).
- A **data** edge exists when a node reads the value via `input_keys` (STATE) or
  `pool_inject` (POOL).

**Kind is a property of the edge, not the binding** — a single binding can carry
edges of both kinds. The triggering agent's `evaluation` is the canonical case:
it has a *control* edge (the loop branches on the evaluator's returned decision,
`plan_execute_runner.py:475`) **and**, after Phase 0, a *data* edge (the
synthesizer reads `evaluation` from STATE — every agent execution writes its
`output_key`, `harness.py:720`). A binding is **live iff it has ≥1 consumption
edge of any kind**.

- **availability ∈ {always, maybe}.** `always` = produced on every path to the
  read; `maybe` = produced only by some branches (e.g. one arm of a
  conditional, or a loop body that may run zero times). This lattice already
  exists (`_mark_new_bindings_maybe`, `condition_contracts.py:286`).

### 2.2 Lexical scoping = resolution change only

Resolution rule: a read in node N resolves against **N's own scope plus the
bindings explicitly imported into N's enclosing block** — *not* the flat union
of every binding produced anywhere earlier. Outer-block bindings are hidden
unless exported across the block boundary.

Because reads get serialized copies of immutable entries (§1.4), this changes
*which name resolves*, never *what is stored*. A workflow that today
accidentally reads an outer-block key it never declared as an import will now
fail the checker — which is the point (less permissive).

### 2.3 Auto-derived imports/exports (freevars)

We do **not** ask the builder to author import/export lists. We compute them:

- **Imports of a block** = the *free variables* of that block = the set of keys
  read by any descendant that are **not** produced by any binding inside the
  block. (Standard free-variable analysis over the scope tree.)
- **Exports of a block** = the bindings produced inside the block that are read
  by any node *outside* it. By default a block exports exactly what its parent
  (or siblings) actually read; everything else stays block-local.

This means current generated workflows keep working unchanged: their existing
`input_keys`/`output_key` declarations *are* the import/export signal. The
scoping only starts *rejecting* things that were already latent bugs (a read
with no producer anywhere in scope).

### 2.4 Worked example — the triggering agent

```
plan_and_execute "plan-and-execute"          scope: {query, coordination}
├─ planner            out: research_plan      binds research_plan (data)
├─ (item injection)   out: current_step       binds current_step (data, container-injected)
├─ body = sequence "research-body"            scope inherits {query, coordination, research_plan, current_step}
│  ├─ researcher      in: [query, current_step, research_plan]   out: findings (data)
│  │                  pool_writes: observations, sources
│  └─ reflector       in: [query, current_step, findings, research_plan]  out: reflection (data)   ← DEAD STORE
│     pool_inject: observations
└─ evaluator          in: [query, current_step, findings, research_plan]  out: evaluation
                      return value → CONTROL edge consumed by the loop (plan_execute_runner.py:475)
synthesizer           in: [query, research_plan, findings, reflection]   ← reads the dead store
```

Checker verdict (post-fix-design):
- `evaluation` carries a **control** edge (the loop branches on the evaluator's
  returned decision, via the RUNTIME-RETURN channel). Without modelling channel
  3 it would be a false-positive dead store.
- `reflection` carries only a **data** edge (read by the synthesizer). After
  Phase 0 removes the body reflector and repoints the synthesizer to
  `evaluation`, `reflection` ceases to exist; the synthesizer's read then
  resolves to `evaluation`, which is live (control edge + the new data edge).

## 3. The checker — two passes over the Scope Tree

### 3.1 Pass A — dangling reads ("read from nowhere")

For every read, resolve it against the reader's scope (§2.2). If no binding
exists, it's a **dangling read = error**.

Three seeding rules prevent false positives (all confirmed necessary by
adversarial review, §6):

1. **Container-injected dynamic keys.** `plan_and_execute` injects
   `current_step` (its `item_state_key`) with no `output_key` producer
   (`plan_execute_runner.py:378`). The plan_and_execute validator *already*
   seeds this binding (`condition_contracts.py:323-328`) — Pass A reuses that,
   and the same applies to any future container that injects a per-iteration
   key.
2. **Runtime-derived & bookkeeping keys.** Seed the producer set with
   `state.py`'s `_RUNTIME_DERIVED_KEYS` (`{claims, verification_summary,
   analysis_summary, verification_details}`, `state.py:30-37`) plus the runner's
   bookkeeping keys (`observed_tool_kinds`, `missing_required_tool_kind_groups`,
   `last_blocked_step` — `plan_execute_runner.py:419-428`). These are produced
   by the runtime, not by any node's `output_key`, so a reader of them is not
   dangling.
3. **Pool names are not state keys.** `pool_inject`/`pool_writes` resolve against
   the POOL channel, never STATE. Exclude pool names from STATE dangling-read
   checks (a pool injection is not a state read).

Roll-out: **lint first, strict second.** Pass A ships as a warning, we measure
the corpus of generated workflows, fix the builder's real dangles, then flip to
error.

### 3.2 Pass B — dead stores ("nothing wasted"), severity-tiered

A binding is a **dead store** iff it has **zero consumption edges** (§2.1) of any
kind. For each dead store, classify by what the producer *is*, to assign
severity:

| Producer / consumer situation | Verdict |
|---|---|
| A **container control source that does not resolve** — a loop `until` key, a conditional branch key, or a plan_and_execute evaluator slot whose key has **no producer** | **error** — the container cannot make its decision ("a controller with no signal"); realized as a dangling *control read* in Pass A |
| A plain data `output_key` read by nobody | **warning** — wasted compute, not incorrect |
| Top-level workflow result (e.g. synthesizer `report`) | **exempt** — the workflow's output is *supposed* to be terminal |
| A `pool_writes` whose pool a *later* node injects | **exempt** — see §3.3 (this binding is **not** dead; it has a POOL data edge) |

The error tier is a **dangling control *read*** (a container needs a control
signal that no node produces), **not** a "dead control *producer*." We
deliberately do **not** flag a reflector/evaluator whose decision is consumed
only as *data* — e.g. the legitimate `coverage-reflector → finalizer`, or the
pre-fix body reflector → synthesizer. The framework cannot structurally
distinguish "useful critique" from "wasted reflection"; that is a semantic
judgment, not a dataflow violation (the §1.1 body reflector is removed by Phase 0
judgment, not caught by the checker — a subtype-based "redundant decision-maker"
check would false-positive the legitimate `coverage-reflector`). Because a
binding with even one live edge of *any* kind is not a dead store, the
post-Phase-0 `evaluation` (control edge + data edge) is unambiguously live.

### 3.3 The interior-observation exemption

A researcher may `pool_writes: observations` purely so a *downstream* synthesizer
can `pool_inject: observations`. The producing node never reads it back; the
consumer is far away in the tree. This is a legitimate POOL-channel data flow,
not a dead store. Pass B must resolve POOL reads/writes globally (pools are
workflow-scoped, not block-scoped) before flagging a `pool_writes` as dead.

### 3.4 Loop-carry fixpoint

A loop body can read a key that a *later* iteration's body produced (loop-carried
dependency). A single forward pass — which is what `_validate_loop_node` does
today (`condition_contracts.py:281-287`, one pass over children, no fixpoint) —
will false-positive on the first iteration's read. Pass A/B must run a
**2-pass fixpoint** over loop and plan_and_execute bodies: pass 1 collects all
bindings the body produces (across iterations), pass 2 resolves reads against
that fixed point. Equivalently, extend the existing `maybe` guard
(`condition_contracts.py:431`) so loop-body reads of loop-body-produced keys are
treated as `maybe`-available rather than dangling.

### 3.5 Why a tree is checkable (and a graph would not be)

The composition is a **tree**, not an arbitrary graph. That is what makes all of
the above decidable in two linear passes:

- Scopes nest; free-variable analysis is a single bottom-up walk.
- "Later in the tree" is a well-defined execution order (sequence = ordered,
  parallel = unordered-but-joined, loop = fixpoint, conditional = branch
  lattice). There are no back-edges except the *structured* loop carry, which
  the fixpoint handles.
- An arbitrary DAG with cross-edges would need general reaching-definitions and
  could express cycles the runtime can't actually execute. The tree's
  structured control flow is exactly the subset we can both **synthesize
  freely** and **check completely**.

## 4. Visualization — one IR, two renderers

The Scope Tree IR is the single source of truth, rendered two ways:

1. **Human DAG.** Nodes = workflow nodes; edges = the three channels
   (STATE solid, POOL dashed, CONTROL bold). Dead stores flagged red, dangling
   reads flagged with a broken-edge glyph. Block scopes drawn as nested boxes so
   the import/export boundary is visible. Rendered in the agent-designer UI.
2. **Repair-LLM text.** The same IR serialized as a compact textual dataflow
   summary ("node X produces K (data, read by Y, Z); node W produces C (control,
   UNREAD ← error)"), handed to a repair LLM when the checker fails so it can
   patch the topology. This closes the generate→check→repair loop.

Both renderers consume the *same* IR the checker produces — no second
derivation, no drift between "what the checker saw" and "what the human/LLM
sees."

## 5. Phasing

### Phase 0 — Fix the triggering agent's builder (decided)

In `workflow_builder.py` `_build_plan_and_execute_workflow`:
- **Delete** the body `reflector` node (`:1925-1945`) and make the body the
  direct researcher (`body = researcher`, removing the `make_sequence` wrapper
  at `:1946-1950`). This matches the docstring's stated shape (`:1809`) and
  removes one analytical-tier LLM call per research step.
- **Repoint** the synthesizer's `input_keys` from `reflection` → `evaluation`
  (`:2012`), so the synthesizer reads the live evaluator output instead of the
  deleted reflector's dead store.
- Update/add builder unit tests asserting the body is the direct researcher and
  the synthesizer reads `evaluation`.

This is independent of the checker and ships first as the concrete win.

### Phase 1 — Scope Tree IR + Pass A (dangling reads), lint → strict

Build the Scope Tree IR (extending `condition_contracts.py`'s scope/binding
vocabulary). Implement Pass A with the three seeding rules (§3.1). Ship as lint,
measure the generated-workflow corpus, fix real dangles in the builder, flip to
strict.

### Phase 2 — Pass B (dead stores) with control-edge modelling

Model the RUNTIME-RETURN channel as a first-class **control** binding (§1.2,
§2.1). Implement the severity-tiered dead-store check (§3.2), the
interior-observation exemption (§3.3), and the loop-carry fixpoint (§3.4).
control=error, data=warning.

### Phase 3 — Visualization

Emit the IR's two renderers (§4). Wire the DAG into the agent-designer UI; wire
the text renderer into the repair path.

### Phase 4 — Spike: is `plan_and_execute` a macro?

Investigate whether `plan_and_execute` can be expressed as
`planner → loop(body, until=evaluator-decision)` once CONTROL edges are
first-class. If the checker can see the evaluator's control edge, the bespoke
container may reduce to composable primitives. Spike only — no commitment to
refactor in this spec.

### Phase 5 — Structured freedom (gated)

Once Pass A+B measure **zero false negatives** across the topology×domain matrix
(the gate), let the frontier model synthesize free-form topologies (typed-node
ASTs) instead of selecting from the catalog. Every synthesized workflow must
pass the checker; failures route to the repair LLM with the §4 text IR. The
catalog becomes a fallback, not the ceiling.

**The gate is non-negotiable:** a false negative (checker passes a broken
topology) is strictly worse than the catalog's limited expressiveness, because
it ships a silently-wrong workflow. We do not unlock Phase 5 on a checker we
haven't measured complete.

## 6. Risks & how the design answers them

Three reliability gaps were identified by adversarial review (3 independent
skeptics, high-confidence consensus) and are answered above:

1. **STATE-only checking is unreliable** → model RUNTIME-RETURN as a
   first-class control edge (§1.2, §2.1, Phase 2). Without this the checker
   false-positives the evaluator as dead and false-negatives the body reflector
   as live.
2. **Single forward pass false-positives loop carry** → 2-pass fixpoint
   (§3.4), extending the existing `maybe` lattice rather than replacing it.
3. **Container-injected & runtime-derived keys look dangling** → three seeding
   rules (§3.1), two of which (`item_state_key`, `_RUNTIME_DERIVED_KEYS`) reuse
   logic already in the codebase.

Adversarial finding `breaks_current_structure: no_with_export_decls` — across 7
sampled topologies, scoping with auto-derived exports produced **zero** true
breaks of currently-generated workflows. The risk is false *negatives* in the
checker, not breakage of existing output — which is exactly why Phase 5 is gated
on measured completeness and Pass A ships lint-first.

### Open questions (resolve during writing-plans)

- Exact serialization format for the repair-LLM text IR (§4) — defer to Phase 3.
- Whether `subworkflow` boundaries should be hard export walls or soft
  (defer to Phase 1 freevar implementation; default: subworkflow is a hard
  scope boundary, exports only its declared `output_key`).

## 7. Constitution compliance

- **No hardcoded domains/topologies:** the checker is purely structural (channel
  reachability, freevars, control-vs-data). It contains no domain vocabulary and
  no topology lookup table. Phase 5 *removes* topology hardcoding rather than
  adding it.
- **Generic vocabulary in framework code:** binding keys, pool names, and tool
  kinds are treated as opaque strings; no corpus/table names appear in checker
  code.
- **Prevention over cleanup:** the checker prevents dead/dangling dataflow at
  build time rather than cleaning it up at runtime.
- **Verify attribute names; `make typecheck-framework` before deploy:** all
  citations in this spec were re-verified against current source on 2026-05-29.
